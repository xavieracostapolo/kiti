# R1 — Extensión de VS Code (webview + PixiJS): apertura

## Tesis
El usuario de "Agent Office" lanza `claude`, `codex` y `gemini` mientras programa, y casi siempre lo hace desde un editor. Una extensión pone la oficina donde ya está su atención. Además le da gratis lo que los demás candidatos tienen que construir: terminales reales, árboles y listas nativos, notificaciones, barra de estado, actualizaciones automáticas y distribución sin firmar binarios. Y la prueba de que se puede ya existe: **Pixel Agents** es una extensión de VS Code que dibuja cada sesión de Claude Code como un personaje en una oficina pixel art, con hooks (`SessionStart`, `PreToolUse`, `PermissionRequest`, `Stop`) y, como respaldo, lectura de los JSONL de `~/.claude/projects`. Tiene unas 9.9k estrellas, está en el Marketplace y en Open VSX, y también funciona como CLI independiente con `npx` ([github.com/pablodelucca/pixel-agents](https://github.com/pablodelucca/pixel-agents)). Es casi exactamente nuestro MVP, validado en producción y con este mismo stack.

## Puntuación por criterio

**Integración con el sistema (20%): 8/10.** El extension host es Node.js completo. Tenemos `child_process`, `process.kill(pid, 'SIGTERM')`, `http.createServer` en 127.0.0.1 y `fs.watch` para hacer tail de los JSONL. El nivel de acceso es el mismo que el proceso main de Electron. En remoto, `extensionKind: ["ui"]` hace que la extensión corra siempre en la máquina local ([docs Remote](https://code.visualstudio.com/api/advanced-topics/remote-extensions)). Pierde 2 puntos por dos cosas: cada ventana de VS Code levanta su propio extension host, así que hace falta elegir un líder para el servidor HTTP, y ese host lo compartimos con otras extensiones.

**Capacidad 2D de juego (15%): 8/10.** El webview es Chromium con WebGL. PixiJS y pixi-viewport corren igual que en Electron o Tauri. Pixel Agents lo consigue incluso con Canvas 2D y pathfinding. Pierde puntos porque la escena está dentro de una pestaña o vista y su ciclo de vida lo controla VS Code (ver debilidad 2).

**UI tipo herramienta (15%): 9/10.** Es el criterio donde ningún rival se nos acerca. La "terminal embebida futura" ya existe: `window.createTerminal` lanza el agente en una terminal real de VS Code. `Terminal.processId` nos da el PID. La API de shell integration (`onDidStartTerminalShellExecution`) es estable desde la 1.93 ([release notes](https://code.visualstudio.com/updates/v1_93), [API](https://code.visualstudio.com/api/references/vscode-api#Terminal)). Además tenemos TreeView para listar agentes, OutputChannel para logs, QuickPick y diffs nativos. Electron y Tauri tendrían que integrar xterm.js y node-pty, con módulos nativos que hay que recompilar en cada plataforma.

**Multiplataforma y distribución (15%): 9/10.** Un `.vsix` en JS puro sirve para macOS, Windows y Linux. Se publica con `vsce` en el Marketplace y con `ovsx` en Open VSX, y desde ahí lo usan Cursor ([docs Cursor](https://cursor.com/docs/configuration/extensions)), Windsurf y VSCodium. No hace falta notarizar con Apple, comprar un certificado de Windows ni montar un updater. Si algún día necesitamos binarios nativos, hay VSIX por plataforma con `--target` ([publishing](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#platformspecific-extensions)). Pierde 1 punto por tener que publicar en dos registros y por el riesgo de licencias entre Microsoft y los forks ([DevClass](https://www.devclass.com/development/2025/04/08/vs-code-extension-marketplace-wars-cursor-users-hit-roadblocks/1629343)). Ese conflicto afecta a extensiones cerradas de Microsoft, no a las de terceros.

**Consumo de recursos always-on (10%): 6/10.** Si el editor ya está abierto, el costo extra es un renderer de webview y algo de CPU en el host. Pero la propia documentación dice que los webviews son *resource heavy* y que `retainContextWhenHidden` tiene "high memory overhead" ([guía Webview](https://code.visualstudio.com/api/extension-guides/webview)). Si el usuario no tiene VS Code abierto, el costo real es el de todo VS Code. Ahí Tauri gana.

**Velocidad de desarrollo y soporte de LLMs (15%): 9/10.** TypeScript, la API de VS Code y PixiJS están entre lo que mejor conocen los LLMs. Con F5 se abre un Extension Development Host con recarga en segundos. Y tenemos un repositorio de referencia del mismo dominio para estudiar.

**Madurez y riesgo (10%): 8/10.** VS Code tiene una API estable con compatibilidad hacia atrás y sale una versión al mes. El riesgo de fondo es atar el producto a un editor y a su ecosistema de forks.

**Ponderado aproximado: ~8.2/10.**

## Mis 3 debilidades más serias (y cómo las mitigo)

1. **Necesita el editor abierto, y no todo dev vive en VS Code.** Quien trabaja con Ghostty, iTerm o tmux, o usa JetBrains, queda fuera. *Mitigación:* separar el diseño en tres paquetes. `core` (Node puro: detectar procesos, servidor de hooks, tail de JSONL) no sabe nada de VS Code. `ui` (PixiJS) se comunica solo por `postMessage`, con la misma forma de mensajes que un WebSocket. El adaptador de VS Code es fino. Pixel Agents ya hace lo mismo con su modo `npx` en el navegador, y así un shell de Electron o Tauri más adelante reutiliza el 90% del código.
2. **Varias ventanas y ciclo de vida del webview.** N ventanas implican N extension hosts y choques de puerto. Además, cuando la pestaña se oculta, el webview se destruye. *Mitigación:* elegir líder con un lockfile y un puerto fijo, y que las demás ventanas se conecten como clientes. El estado vive en el host y la escena se reconstruye desde un snapshot con `getState/setState` y un `WebviewPanelSerializer`. `retainContextWhenHidden` se reserva para el panel de la oficina, conscientes de su costo.
3. **Techo de producto como "app".** No hay ventana libre ni always-on-top, ni bandeja del sistema, ni atajos globales. La oficina está metida en una pestaña o en el sidebar, y el CSP obliga a trabajar sin scripts inline. *Mitigación:* usar notificaciones nativas, un badge en la barra de estado ("2 agentes esperando permiso"), arrastrar el panel a una ventana flotante del editor y un CSP estricto desde el día uno con `webview.cspSource`. Si el producto pide una ventana independiente, eso es justo la migración del punto 1.

## Ataques previsibles y respuesta

**A1 (Tauri): "VS Code pesa cientos de MB; para algo always-on, un WebView nativo con Rust consume una fracción."** Es cierto si comparamos instalaciones en frío. Pero quien usa Agent Office ya tiene un editor abierto todo el día, y el costo extra es un webview. Tauri, además, obliga a escribir en Rust (o en un sidecar) la gestión de procesos y señales que Node ya trae, a firmar y notarizar en tres sistemas y a mantener su propio updater. El WebView de Linux (WebKitGTK) también es menos predecible con WebGL que el Chromium de VS Code. Para un solo dev, eso es tiempo que no se dedica al producto.

**A2 (Electron): "Es tu mismo stack sin depender del editor. ¿Para qué encerrarse?"** Coincido en el stack, y por eso la arquitectura del punto 1 hace que pasar a Electron sea barato. La pregunta es por dónde empezar. Electron exige empaquetar unos 100+ MB por plataforma, firmar, manejar el auto-update y construir la terminal con node-pty. La extensión llega a usuarios reales desde la primera semana, con instalación de un clic en VS Code, Cursor y Windsurf, que es justo donde se usan Claude Code y Codex. Primero se valida el producto y luego, si hace falta, se le da un binario propio.

*(Godot y Flutter+Flame tienen mejor motor de juego que PixiJS, pero cojean en los criterios de mayor peso: procesos y sockets sin Node, terminal embebida y UI de herramienta densa en texto.)*

## Riesgo competitivo (honestidad)
Pixel Agents ya cubre Claude Code en VS Code y tiene Codex y Gemini en su roadmap. Eso valida el stack, pero también significa que el diferenciador tiene que ser **multi-agente desde el MVP**, el semáforo de estados, matar procesos y los paneles de herramienta, no solo "personajes en una oficina".
